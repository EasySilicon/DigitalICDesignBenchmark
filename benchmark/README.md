# Digital IC Design Benchmark for Agents

[English](README.en.md)

Digital IC Design Benchmark for Agents 是一套数字芯片设计与交付 benchmark，用于比较多 Agent 系统与通用 coding agent 的完整 RTL 交付质量。它包含 10 个任务，覆盖组合逻辑、时序控制、片上总线、CDC、缓存、五级流水线 CPU 和多精度 NPU 矩阵乘法。每题要求 Agent 自行完成 RTL、可运行验证环境和 PPA 优化迭代。全题的物理目标为 1000 ps / 1 GHz；PPA 基线按任务通过发布门禁后逐题启用，当前 T01–T09 已完成，工具镜像和整套发布证据仍须继续冻结。

跨题任务规则、交付契约、验收、评分、PPA 与覆盖说明以本 README 为统一入口；各题的冻结题面和专属验收要求仍以其 `tasks/Txx/` 目录为准。

## 范围与工具

功能验收使用预装的 Verilator、Yosys、Python/cocotb、RISC-V 裸机工具链及 Sail/ACT4；PPA 评估使用 Yosys + ASAP7 + OpenROAD，不单独依赖其他 STA 程序。不以商用 EDA 许可为参赛前提。本机已安装 OpenROAD 26Q2-1164-g08f67ee5ec 和 Yosys 0.69+150，并已用仓库内 ASAP7 跑通 T01–T09 参考设计的三种子详细布线与活动功耗链。当前参考三元组只用于试评分，尚无正式榜单。SystemVerilog testbench、适用的 SVA 和 Verilator 覆盖率均可作为参赛交付物。评测器必须先用实际固定版本运行每项语法、覆盖率和 UVM 依赖的冒烟测试；不能仅凭工具名称假定所有语法都可运行。

本规范评估可综合 RTL 的功能正确性、统一开源物理流程下的 PPA 估计及完成时间，也记录验证交付质量；不声称流片签核、模拟电路或正式 RISC-V 认证。PPA 只有在工具镜像、工艺、约束、活动负载和参考值校准完成后才参与正式排名。

## 通用验收规则

本文件将各[任务卡](#共享任务规则)的 F/P 子项落实为测试组。表中的场景是**应覆盖的行为类**，不能仅凭表格视为已通过发布门禁。T01–T09 已完成任务级 1 GHz PPA 基线校准，T10、工具镜像和整套发布门禁仍待完成，因此目前不生成正式榜单。[端口冒烟与独立验收器](../evaluator/README.md)的源码随仓库公开；正式试做时，只把任务材料和公开冒烟复制进被测 Agent 的工作区，验收程序与种子不进入该工作区。每组测试必须有独立 oracle、超时上限和失败时的最小复现日志。

任务专属的测试组、参考模型和缺陷类别位于各任务目录中的 `acceptance.md`；以下只列跨题共享规则和任务索引。

### 通用规则

- 每个 `AC-xx` 组映射到任务卡列出的一个或多个 F/P 子项，评分脚本保留组与子项的双向映射。场景重复不能重复得分。
- 时序题的驱动在非采样沿改变，沿后经过一个仿真 delta 再比较；组合题改变输入后等待组合稳定。两个时钟域分别按各自时钟的采样规则运行。
- 公开冒烟提供至少一个 PASS 轨迹与一个故意失败轨迹的预期日志；独立验收失败必须输出任务 ID、组 ID、种子、首次失败周期/事务、输入与期望/实际。
- 所有随机流由固定种子生成，生成器校验自己输出满足协议假设。参考模型只根据已接受事务更新，不窥探 DUT 内部状态。
- 对被测 RTL 的超时取该组参考实现最坏周期的至少 5 倍；含外部可变延迟的组使用任务卡上限建模。超时阈值在正式版锁定，不依据参赛者表现改变。

## 验证与交付契约

本契约随十题[任务卡](#共享任务规则)发给每个参赛 Agent。**每题的工作范围同时包含 RTL 设计、自带验证环境、修复缺陷和 PPA 优化。** Agent 可自由选择 SystemVerilog/UVM、SVA、cocotb、C++ 或组合实现 `verif/`；评测方的功能结论来自独立编写的验收器，与其 UT 框架无关。

### 参赛提交及本地入口

| 制品 | 必要内容 | 评测用途 |
| --- | --- | --- |
| `rtl/` | 可综合 `.sv/.v` 源码；单一约定顶层，所有设计功能经题卡端口体现 | 独立功能验收、统一 Yosys/OpenROAD PPA |
| `rtl/files.f` | UTF-8 文本，每行一个位于 `rtl/` 内的相对源文件路径；不含命令选项、宏、绝对路径或 `..` | 评测器安全地读取源码清单并自行编译 |
| `verif/` | Agent 自建的可执行自检，包括至少一个会判断预期与实际值的测试；T02–T10 应覆盖各自题卡主要行为类 | 检查完整验证交付，运行变异体诊断测试质量 |
| `run.sh` | 可执行、无交互的本地自检入口；默认从仓库任务工作区运行，不下载依赖 | 检查自检可重复执行，供 Agent 日常迭代 |
| `README.md` | 构建/运行说明、自检范围、已知限制、设计取舍和 PPA 优化记录 | 审计交付过程，不凭文字给功能分 |

`run.sh` 从工作区根目录调用；返回码 0 表示自检通过，非零表示失败。支持 `BENCH_SEED` 环境变量，未设置时用文档写明的固定默认种子；运行结果写入当前目录的 `results.json`。该文件至少含 `tests` 数组，每项包含 `name`、`passed`、`seed`；`seed` 是该项实际使用的整数种子，允许从 `BENCH_SEED` 确定性派生多个种子。同一个场景名可以在不同 seed 下重复，测试实例以 `(name, seed)` 唯一标识。另含 `tool_versions`、`elapsed_seconds`。可以包含 UVM、断言、覆盖率、波形和详细报告，但不能要求评测器理解其内部格式。评测方分别运行两次相同种子检查结果可重现，再用其公开的故意错误样例确认自检确实失败。Agent 可以在时限内反复执行该入口，**这些运行均计入开发时间**。

T09 还须支持 `./run.sh --elf /absolute/path/program.elf`：Agent 的验证环境加载任意符合题卡内存布局的 RV32 ELF，运行至 `tohost` 或超时，返回 0 当且仅当 `tohost=1`，并在 `results.json` 给出 `elf_sha256`（十六进制 SHA-256）、`tohost`（整数）、`timed_out`（布尔值）和失败时非空的 `failure_reason`。**Agent 无需生成逐指令 trace 文件或实现 trace 采集器。** `--elf` 模式不得靠文件名、固定 PC 或预知程序输出判定 PASS。此接口用于验证 Agent 交付的 ELF 运行能力；官方 CPU 功能分仍由评测方自己的 ELF 装载器、总线模型、ACT4/差分程序取得。

Agent 可以使用预装 Yosys、OpenROAD、ASAP7 和 ORFS 脚本反复测自己的 RTL，并据此优化面积、布线后路径和能耗。`README.md` 记录至少一个优化候选与最终选择，以及实际运行的工具命令、配置 hash、测量值或失败日志。对小题和首次即最优的设计，允许保留原实现并说明测量证据；**不要求每题都证明正向改进**。正式 PPA 由评测方统一重跑，参赛者的 SDC、种子、报告和自测分数均不直接进入排名。

### 官方验收器与参赛 UT 的关系

| 对象 | 谁实现 | 如何判断 | 是否进入正式功能分 |
| --- | --- | --- | --- |
| 自带 UT | 参赛 Agent | 入口是否运行、自检是否真实、变异体检出率及需求覆盖记录 | 作为交付准入和质量诊断；不替代独立功能分 |

| T09 独立验收器 | benchmark 团队 | 自有 ELF 装载器、存储器模型、ACT4、定向程序、逐条取指至退休延时和提交差分；流水线分由可观察时序组合门禁自动判定 | 是，F+P 原始权重 75，归一化功能分 50 |
| T10 独立验收器 | benchmark 团队 | 自有矩阵向量生成器和精确数值模型核对固定端口；持续输入、四槽稳态输出、块 ID、背压和脉动 PE 网格自动检查 | 冻结参考 RTL 已通过 2,752 块及 704,512 个输出点验收，14/14 个缺陷变异体已检出；完整顶层 PPA 基线完成前只启用功能试评分 |
| 统一 PPA 流程 | benchmark 团队 | 固定工艺/约束/活动负载，布线后重测 | 功能全过且满足测量来源门禁后计 PPA /50 |

每题都需要评测方的**独立、可自检的 UT 环境**，包括 CPU 和 NPU；ACT4 只能覆盖适用的 ISA 规则，不能检验题卡自定义总线、精确提交或五级流水线。评测方通过输入波形、事务和外部参考模型验收 RTL，故 Agent 的 UT 风格可以差别很大。T05 的双级同步器和 T10 的 PE 邻接网格需要自动静态检查；T09 按取指至退休延时、相关、冲刷与提交轨迹评估可观察五级时序，不能凭端口数学证明内部恰有五级。逐提交 F/P 分只由脚本和固定规则生成，不要求人工复核；参考 PPA 基线可在发布前人工核查。

## 评测与评分方法

### 目标和实验轨道

主要问题是：在同等可见信息、工具和预算下，多 Agent 系统是否提高**一次提交的可验收交付质量**。排名严格按**功能正确性 → PPA → 完成时间**，具体规则见下文。产品轨道让各系统使用其原生模型，以相同费用和时限比较实际产品效果；控制轨道仅纳入能接入同一基础模型快照、采样设置和 API 的系统，用于分析编排和工程流程的影响。两条轨道的分数不得合并，也不得由产品轨道的差异单独归因于多 Agent 编排。每个任务至少独立运行 5 次，随机种子预先固定且各系统相同；报告逐题中位数、一次通过率、平均分、成本和耗时，而非只挑最好的一次。

各运行从同一只读起点复制为独立工作区。Agent 看到完整规范、任务包内的公开冒烟和本地工具；仓库公开的独立验收器、参考 RTL、变异体及评分脚本不复制进受测工作区。禁止在执行中访问其他参赛工作区、评测服务或历史解答。所有系统都可自选内部角色数和分工；计费 token、工具调用、并行资源和时钟均计入同一上限。

每题须启动**全新会话**，只注入该题的固定提示和公开文件；上一题结束后保存提交快照与计时日志，再销毁其会话和可写工作区，下一题不得调用 `resume`、`fork` 或读取历史对话。对 Codex CLI，试跑使用每题一个新的 `codex exec --ephemeral` 进程。[官方 CLI 参考](https://learn.chatgpt.com/docs/developer-commands?surface=cli)将 `--ephemeral` 定义为不把会话记录持久化到磁盘；它不能隔离文件系统。正式评测还须给每题独立容器或等效权限边界，使用本题专属临时用户配置目录，只注入相同的只读工具配置与认证；挂载只读公共起点和本题可写目录，屏蔽其他题、历史解答、全局记忆及正式验收目录，并在任务结束后撤销访问。仅靠更换工作目录或提示词不得宣称完成环境隔离。验收器、参考 RTL 与变异体本身随完整仓库公开；这里的“屏蔽”仅指不得向正在受测的 Agent 泄漏答案材料。

### 资源约束

| 项目 | 固定规则 |
| --- | --- |
| 单次运行计算资源 | 16 vCPU、32 GiB RAM、100 GiB 可写盘；无 GPU、无 FPGA、无商用 EDA 许可 |
| 网络 | 仅允许事先声明的模型 API；依赖、工具链、ACT4 及参考资料均预装并锁版本 |
| 开发时钟 | 从题目与工作区交付开始计时；[清单](manifest.yaml)中的各题时限到点自动冻结文件快照 |
| 模型预算 | 控制轨道按[清单](manifest.yaml)中的累计输入+输出 token 上限运行；产品轨道按同一美元推理费用上限运行，费用上限须在模型与单价快照确定后统一公布 |
| 工具预算 | 同容器、同 CPU/RAM 限额；编译、仿真和脚本都计入时钟与资源用量 |
| 提交 | `rtl/`、`rtl/files.f`、`verif/`、`README.md` 和一个无交互 `run.sh`；由评测器冻结并复制到隔离环境；接口按[验证与交付契约](#验证与交付契约) |
| 硬件资源 | 各题见[任务卡](#共享任务规则)。RTL 必须可综合，不得靠测试环境 DPI、文件 I/O、延时或未声明的黑盒实现功能 |

上表中的时限和控制轨道 token 上限是首轮工程预算，发布前须试做校准；产品轨道的美元上限尚待模型与价格快照，因此 **v0.2 不允许据此宣称公平的正式排名**。模型调用记录必须能审计输入、输出 token 和费用，但不得泄露题目隐藏数据。

#### 工具链锁定

评测镜像应固定 OCI digest，以及 Verilator、Yosys、OpenROAD、ASAP7 工艺文件、C++ 编译器、Python/cocotb、RISC-V GCC/LLVM、Sail、ACT4 的精确修订；不单独依赖另一套 STA 程序。默认以本机 Verilator 5.051 devel 做兼容性预检；正式评测使用一个确定的镜像，不跟随本机升级。每个任务的参考实现、公开测试、隐藏测试和 PPA 流程都在该镜像内试运行。UVM、SVA 和覆盖率能力按**实际使用的语法**做冒烟验证，测试运行时不得将不支持的语法静默屏蔽。

### 输入、输出与规范优先级

原创题以[任务卡](#共享任务规则)为唯一规范，公开测试只是示例，不得反向增加限制。所有时序要求以有效时钟沿前采样输入、沿后检查寄存输出为准；握手在上升沿 `valid && ready` 时发生。未规定的非法输入不计分，除非任务卡写明结果。

`run.sh` 要返回非零退出码报告失败，固定随机种子可由环境变量 `BENCH_SEED` 覆盖，输出一份机器可读 `results.json`，包含测试名、通过状态、种子、工具版本、耗时；T09 还须提供 `--elf` 入口，详见[契约](#验证与交付契约)。Agent 在同一时限内必须自行编写验证环境、用其定位并修复 RTL 缺陷，并使用本机 PPA 工具探索至少一个候选实现或配置效果；PPA 约束不可作为提交物覆盖官方配置。完成时间从题目发放开始，到参赛系统明确提交最终文件快照为止；到点未提交则冻结当时文件。该时间包含模型推理、内部协作、编译、仿真、PPA 探索和重试，排除评测器排队与隐藏测试运行。禁止修改评测器、隐藏测试、工具二进制或检查脚本；检测到改动或试图读取隔离路径，整次运行记 0 并记录证据。其他失败应按下面的分项规则保留部分分。

### 分层评分与排名

每题保留便于阅读的 105 分显示分，但**正式排序使用分层比较**，不能用总分把功能缺陷与 PPA 或速度互相抵消。

| 层级 | 显示分 | 进入条件 | 自动验收方式 |
| --- | ---: | --- | --- |
| ① 功能正确性 F+P | 50 | 所有有效提交 | 通常 F=60、P=15；T09 为 F=48、P=27，其中独立周期组占 10 分。原始权重均乘 `50/75`，功能总分仍为 50 |
| ② PPA | 50 | 功能=50 且通过综合/接口与测量来源门禁 | 统一 PDK、SDC、活动负载下测面积、关键路径和每有用操作能耗；算法见[PPA 方法](#ppa-测量与评分) |
| ③ 完成时间 | 5 | 功能=50 且 PPA 有效 | `5 × (1 − t/T_max)`，裁剪到 0–5；`t` 是最终提交墙钟时间，`T_max` 为该题时限 |

每个 F/P 子项只有在其定义的测试组通过时得分；随机测试以预先固定、但不随任务工作区提供的种子组执行，**不得按测试数量让某一细节主导权重**。T08 保留其已冻结的组内场景比例计分：每个场景须三个功能种子全过才计入通过数。T09 的 22 项周期检查独立成组：全过得 10 分，通过 11–21 项得 5 分，通过 0–10 项得 0 分；其他原有组按原比例缩放至合计 40 分，不重复合并周期失败。其他题目单项可设 0、半分、全分三个档位：全部通过取全分，至少一半的独立场景通过且无错误接收/错误提交等安全类缺陷取半分，否则 0。安全类缺陷所在子项直接 0。任务包内公开冒烟的分数不超过功能原始权重的 20%；独立验收给出可重现失败摘要，但不向受测 Agent 工作区提供全部向量。**只有归一化功能分为 50 才算功能全通过**；其余运行的 PPA、时间显示分均为 0，但仍记录诊断测量。

若 Agent 宣布完成后，其冻结提交在干净交付环境中因候选自身原因无法完成入口运行（例如 `run.sh` 因未声明变量退出且未生成 `results.json`），每个经评测方裁定的独立根因从 105 分显示总分固定扣 5 分。同一根因被确定性复跑多次仍只计一次；评测器误判、工具缺失或基础设施故障不计。该固定扣分不再把已经有效测得的 PPA/时间分整块清零。报告须同时保存原始分、错误数、扣分和扣分后显示分。

**单题排序**依次比较 `(功能得分，PPA 排名分档，完成时间较短者优先)`。PPA 原始分照常报告；排名时按预先冻结的分辨率 `q` 计算 `PPA 排名分档 = min(floor(50/q + 0.5), floor(PPA 原始分/q + 0.5))`，同档才比较时间。试评分 `q=1.25` 分，与原 20 分制的 `q=0.5` 保持同一相对分辨率；正式版仍须用跨机器和跨工具重复性数据复核。采用分档使排名具有一致、可传递的顺序。**套题排序**先比较功能全通过题数，再比较十题功能总和；仍相同时比较所有功能全通过题的 PPA 排名分档总和，最后比较这些题的 `t/T_max` 总和。若全通过题集合不同，PPA 均已按各题参考设计归一化；同时报告逐题数据。105 分显示分只用于可视化，不作为排序键。

#### 交付准入与失败处理

1. 找不到顶层、独立功能仿真无法编译/展开或接口不符时，F+P=0；保留诊断日志。Yosys 综合/结构网表生成失败不等同于功能仿真无法展开，按下面的异常判分规则分别处理。候选 RTL 有锁存、仿真专用捷径、未声明黑盒，或在综合路径使用 `#delay`、`force`、文件 I/O 时，不可进入 PPA 排名，并标记交付不合格。
2. 参赛系统必须提交可运行的自检入口、至少一项自检、使用说明、PPA 探索记录和可综合 RTL。T09 的自检还须加载评测方提供的任意合法 ELF。缺失或入口无法完成时，独立功能与物理测试仍运行并保留有效分数，同时标记为**交付不合格**；候选原因的致命交付错误按上面的固定规则扣显示总分。自检质量的变异检出率另作诊断；正式阈值须经变异体校准后冻结。
3. **行为 oracle 不得依赖 DUT 内部信号**。自带断言可观察内部设计；独立行为评分通过约定端口和 CPU 提交端口进行。T05 的双级链与 T10 的脉动 PE 邻接结构按冻结的自动网表规则检查；T09 以端口延时、相关、冲刷和提交轨迹检查可观察的流水线行为。逐提交 F/P 评分全自动，不读取人工评审文件。评测器不执行候选自带验证代码来判断其 RTL 正确性；候选 UT 在单独的交付检查和变异体试验中运行。
4. 功能测试超时或死锁只扣相关功能点，不一票否决其他独立点；CPU 的架构程序与流水线专项分别记分。

架构资源边界（例如不加片内大 ROM、缓存容量不超规格）是功能/交付门禁，单元面积则由统一 PPA 流程比较。静态规则及工具版本在发布前冻结，无法自动判定的实现不得通过人工豁免改变逐提交分数。PPA 参考基线可在发布前由工程师复核；正式评分不依赖人工判断。

#### 异常归因与分项判分

异常不能统一当作功能零分，也不能仅凭 `timeout` 或 `SIGKILL` 判断责任。先保存冻结提交、完整命令、工具版本、阶段日志、退出码/信号、时间与内存上限，以及可获取的峰值资源记录；在相同配置下复核，并区分以下情况：

| 异常 | 判分处理 |
| --- | --- |
| 候选 RTL 的行为错误、死锁或功能测试超时 | 按对应功能子项扣分，保留其他独立子项；功能未全通过时 PPA/时间为 0 |
| 经复核为候选原因的 Yosys 前端、综合或结构网表生成资源超限，或无法完成统一物理流程 | PPA=0、时间分=0；不抹掉已验证的功能分，不凭资源超限认定 RTL 功能错误或语义上不可综合 |
| 验收器缺陷、工具/依赖缺失、机器重启、外部进程误杀，或原因尚不明确的超时/OOM | 受影响分项记 `null`/待评，修复或排除故障后对原冻结提交重评；不处罚候选者 |
| PPA 基线或测量来源尚未合格 | PPA/时间记 `null`；但已经独立裁定的候选 PPA 失败仍明确记 0，不能用基线待定掩盖失败 |
| 候选自检入口的致命交付错误 | 按独立根因扣显示总分 5 分，保留有效独立验收成绩；单纯综合资源超限不额外套用此交付罚分 |

功能仿真与综合/结构检查应分别保存结果。结构检查未完成，不得伪造结构通过或默认给该结构子项全分；未实际测得的功能分继续记待评。评测器异常也不得把其他已经有效测得的分项清零。`0` 表示已判失败，`null` 表示尚无结论，汇总与发布时必须区分。

正式评测须在赛前按任务与工具阶段统一冻结超时、CPU、内存上限及资源超限判定规则，并在参考实现和不同等价 RTL 写法上校准；不得按模型临时调整。增加诊断预算不等于改变正式评分预算，不得改写候选 RTL 或由评测方代做优化。若修复验收器影响评分语义，应版本化并重评全部受影响的冻结提交。

预发布案例（2026-10-05，Kimi K3-256k / T10）：交付自检检查合格，但完整设计的 Yosys 结构网表生成在诊断放宽到 900 秒后仍超时；代码中有 196,608 位 packed vector，192 个时序块对其动态部分写入，独立限内存复核也出现前端资源超限。评测方裁定该次候选的 PPA 为 0，功能成绩继续待独立验收；不代改 RTL、不追加交付罚分。该案例不构成“动态索引一律违规”，也不把 900 秒设为所有任务的正式上限；其中暴露的验收器超时异常中断后续功能评分问题须另行修复。

#### 自带测试与变异测试

每题由 benchmark 团队制作至少 8 个**独立缺陷变异体**，覆盖优先级、位宽、时序、边界、复位等不同错误；T05–T10 的发布目标为至少 12 个，CPU 至少 20 个。变异体只用于评估参赛者的 `verif/`；其生成器随仓库公开，但不放入受测工作区。当前 T05 的 13 个可综合变异体均已被独立验收器检出。只有参考实现通过测试、变异体本身可编译且确实违反规范的变异体才计入分母。记录 `killed/eligible`、参考实现误报数、需求到测试映射和功能覆盖率；这些是**交付质量诊断指标**，不抵消功能、PPA 或时间的排序优先级。

### 验收器独立性和争议处理

- 每题至少有一个与 RTL 结构无关的参考模型；组合题用穷举，顺序题用事务级 Python 模型，CPU 用 Sail/ACT4 加独立提交差分。不能只拿另一个 RTL 实现当唯一 oracle。
- 公布前对参考实现、朴素错误实现和变异体执行测试；参考实现必须全通过，错误实现必须至少在对应点失败。所有隐藏种子和预期结果固定、可重放。
- Verilator 是两态仿真；不能把未知值检查作为唯一检错方法。复位前输出、未复位 RAM 内容和未规定信号不评分。
- 争议只复核规范、评测器及冻结提交。若题目歧义或评测器缺陷影响所有系统，应修订版本号并**重跑全部系统**，不针对单一系统改规则。

### 难度校准

在正式排名前，用至少 2 种 coding agent 各做不少于 3 次独立试运行，并以自动验收的参考实现和缺陷变异体校准评测器。记录完成时间、F+P 得分、常见失败、澄清次数和测试器误判。难度“均匀”以试运行的**预算内通过率区间和对数完成时间**来检查，不能由任务名称主观断定。

### 统计报告

主指标为“功能=50/50”的一次全功能通过率与十题功能全通过题数；仅在上述指标相同或分层比较需要时，比较已通过题的 PPA，再比较完成时间。补充展示逐题 F/P 原始权重及归一化功能分、面积、关键路径、平均功率与能耗/操作、PPA 得分、提交成功率、交付合格率、变异检出率、开发耗时、模型 token/费用及工具 CPU 时间。用相同随机种子配对系统结果，给出置信区间；10 题规模有限，不能仅凭总分的小差距声称统计优势。

### 发布门禁

正式发布版本必须同时具备：10 个冻结题目工作区；10 个可编译参考实现；10 个公开冒烟测试和独立隐藏验收器；变异体集合及有效性日志；固定工具镜像 digest；公开工艺、PPA 约束/负载/参考值、功耗注释率和重复性报告；ACT4 适用清单及 CPU 配置；产品轨道模型及单价快照、统一费用上限；多 agent 独立试运行报告；可复现的一键评分及机器可读报告 schema。PPA 参考基线可在发布前人工复核，逐提交评分不需要人工参与。任一项缺失只可标为设计稿或试运行版，不生成正式榜单。

## PPA 测量与评分

PPA 仅在任务的归一化功能分为 50/50 且 RTL 可综合、测量来源有效时计分；功能错误的低面积实现不获得 PPA 分。交付入口错误单独按固定规则扣显示总分，不抹掉有效 PPA。PPA 满分为 50；参考三元组对应 35 分，面积/延时/能耗的加权比值可把更优实现提高到最高 50 分。正式评估固定使用 **Yosys 综合映射 → ASAP7 7.5T 标准单元 → OpenROAD 布局、时钟树、详细布线、寄生提取及时序/功耗报告**，不单独运行另一套 STA 工具。[OpenROAD 官方流程](https://github.com/The-OpenROAD-Project/openroad-flow-scripts/blob/master/docs/UserGuide.md)和[OpenRCX 文档](https://openroad.readthedocs.io/en/latest/main/src/rcx/README.html)给出这些阶段的能力。综合后的 Yosys 面积/时序只作为诊断；排名使用**布线后**指标。ASAP7 是预测性公开工艺，不等于量产工艺签核。[ASAP7 项目说明](https://github.com/The-OpenROAD-Project/asap7/blob/main/README.md)

全题目标为 **1000 ps（1 GHz）**、WC 角和种子 11/29/47。T05 的 `wr_clk`、`rd_clk` 也各按 1000 ps 约束，但两者是显式异步的独立时钟域；相同标称频率不改变其 CDC 性质。[PPA 基线清单](ppa-baselines.json)按任务记录资格：某题的三种子物理与功耗门禁完成后，该题即可启用 PPA/时间评分，不必等待其余题；整套 benchmark 的发布状态仍须等待十题全部完成。本机使用 Yosys 0.69+150、OpenROAD 26Q2-1164-g08f67ee5ec 和仓库内 ASAP7。正式榜单还须锁定工具镜像 digest、复核不同 RTL 写法的公平性并完成发布门禁。

### 全题统一的参数与例外

所有题目使用同一个 [ASAP7 平台修订](sources.lock.yaml)、工艺库组合、映射脚本、ABC 策略、时钟目标 `T_common=1000 ps`、I/O 延迟比例、驱动单元、输出负载、布局利用率、放置密度、布线层范围、RC 提取规则和三个固定布线种子。`config.mk`/SDC 由评测器生成，参赛者不得改动。**允许随题目变化的只有端口名、位宽、时钟个数和异步 CDC 例外路径的对象集合；数值参数不按候选或任务调优。** T05 的 `wr_clk`、`rd_clk` 各为 1000 ps，但仅切除真正的跨异步时钟域路径，保留两域内部及同步器后级时序。

| 参数族 | 统一 1 GHz 参数 |
| --- | --- |
| 单元库 | ASAP7 7.5T、RVT、NLDM；WC/SS 时序，TT 活动功耗 |
| 映射与负载 | 固定 ORFS ASAP7 配置的 Yosys/ABC、`BUFx2_ASAP7_75t_R` 驱动与 3.898 fF 输出负载 |
| 全局时钟目标 | 所有任务及每个时钟域均为 1000 ps（1 GHz）；T05 的 `wr_clk`、`rd_clk` 虽同频但独立并声明为异步 |
| I/O 与物理约束 | I/O 延迟比例 20%；核心利用率 10%（现有 T01–T09 基线的试跑值，待十题共同复核）；放置密度 0.60 |

上述统一参数并非直接照搬 [ORFS 的 ASAP7 平台配置](https://github.com/The-OpenROAD-Project/OpenROAD-flow-scripts/blob/master/flow/platforms/asap7/config.mk)及[示例 SDC](https://github.com/The-OpenROAD-Project/OpenROAD-flow-scripts/blob/master/flow/designs/asap7/ibex/constraint.sdc)。`CORE_UTILIZATION` 决定初始核心面积目标，`PLACE_DENSITY` 决定放置器的目标密度；二者不是同一个门禁。10% 最初是 PPA 探针和九题试跑采用的默认核心利用率，现有记录没有证明它适用于 T10 或优于其他利用率；它不是题目的功能或商业实现要求。T01–T09 已按这组参数完成三种子 1 GHz 校准；T09 已于 2026-10-09 按新增周期规则重新资格验证并冻结；seed 11/29/47 setup 裕量为 +9.353/+14.899/+9.008 ps，hold 与 DRC 全过，最小裕量仍需如实保留。T10 可用其他利用率作研发探索，但探索结果不得与正式基线直接比较或计分。十题共同复核后再冻结统一值；若统一值改变，已校准题也必须整体重跑。

#### 参数探索与冻结门禁

1. 先在 T01、T04、T09 的独立参考实现上做小规模矩阵试跑，筛去综合失败、布线失败、时序覆盖不足或成本超过评测机资源上限的组合；随后让候选**同一组合**跑完十题参考实现和每题至少一个功能等价的不同 RTL 写法；T10 在功能与物理门禁具备后纳入。不针对某个任务单独放宽周期或更换映射策略。
2. 选择规则事先固定：全部参考设计完成合法映射和详细布线、全部受约束路径有端点、参考设计在共同 **1000 ps** 下 `report_worst_slack≥0`（T05 对两域分别检查，并切除跨异步域路径）、功耗活动注释达标、三种子 PPA 波动可控；如果物理参数有多个合格组合，优先选重复性更好、流程运行成本更低者。当前 OpenROAD 与锁定 ORFS 的 `global_placement -random_seed` 不兼容，因此只对全局和详细布线传种子；这三次重复不等于三次独立放置。保留所有失败组合与选择理由。
3. 冻结工具镜像 digest、Yosys/OpenROAD/ABC 精确版本、ASAP7 文件 hash、完整 `config.mk`/SDC、库角、ABC 脚本与 `-D` 目标、输出负载、物理及 RC 参数、三个种子、参考三元组和 PPA 排名分档宽度。冻结后所有参赛提交以及参考设计都从头用这套配置重跑；不能根据某个系统的表现再调参。
4. 十题中任一参考设计在 16 vCPU/32 GiB 限额下无法运行，或需要专用宏才可布线时，先修正**全套统一参数或任务规模**并重新校准；不得让部分题用另一套工艺配置。参数探索和评测器隐藏运行不计入参赛者完成任务的时间。

每次参数校准还须保存 OCI 镜像 digest、工具与工艺文件 hash、完整约束、三个种子的原始报告、功耗负载 hash、活动注释率、资源峰值和失败日志。某题的参考 RTL 完成功能、三种子物理及功耗门禁且参考三元组可复现后，将结果写入 [ppa-baselines.json](ppa-baselines.json) 并单独启用该题 PPA/时间评分；整套状态只有在十题及不同等价 RTL 写法的公平性复核全部完成后才能提升为 `qualified_1ghz`。

### 统一物理测量

1. 固定的 ORFS/ASAP7 流程使用 Yosys 映射，OpenROAD 完成放置、时钟树、详细布线，OpenRCX 依据锁定规则抽取 RC。小型存储统一映射为标准单元。生成的单元网表须通过短功能回归；若失败，先核查工具与模型，再判定候选设计的综合语义问题。
2. 三个固定布线种子各运行一次；每次记录标准单元面积 `A`、SS 角最坏受约束路径延迟 `D` 和 TT 角能耗 `E`，各指标取三次中位数。`A` 包括寄存器、逻辑、插入的缓冲器与时钟单元，排除填充单元、测试平台和封装。参考基线必须在全部时钟域满足 setup/hold 裕量非负且详细布线 DRC 为 0；候选的负裕量和 DRC 数量仍如实记录并按下文连续惩罚，不丢弃测量。组合题输入到输出仍使用共同 `T_common`；T05 的 `D` 为两域各自最坏路径的较大值。
3. 在固定工作负载上运行**对应种子的布线后网表**门级仿真，把 VCD/SAIF 切换活动与布线 RC 导入 OpenROAD，在 TT 角由其 `report_power` 报告泄漏、内部与切换功耗。换算 `E = P_avg × 窗口时长 / N_ops`，同时公开 `P_avg` 及各分量。活动注释率至少 95%；不足时先修评测流程，不能用缺失活动的低功耗结果排名。
4. 对可复现的候选 RTL 原因（不能合法映射或完成布线、无有效受约束路径、真实活动缺失）记 PPA=0。完成布线但违反 setup/hold 或存在 DRC 的候选仍进入连续评分；工具基础设施失败则用同一配置重跑，不处罚候选者。保存综合、布局、布线、RC、STA、功耗和功能回归的原始日志。即使有布线 RC，所得指标仍是 ASAP7 公开预测工艺上的**相对估计**。

### 固定功耗工作负载

功耗运行使用赛前固定、但不放入受测任务工作区的种子与事务分布；输入不得含规范外行为，且每个设计完成同样数量的**有用操作**。工作负载中的所有响应仍由独立模型检查，不能只测活动。基准实现同样运行。各题有用操作定义如下：

| 任务 | 有用操作与活动覆盖 |
| --- | --- |

| T01 | 一个输出的 10-bit 对齐符号；固定训练、payload、marker、bit slip 与重锁分布 |
| T02 | 一次成功读出且对应先前成功写入；复位丢弃的未读写入不计有效操作，空/满与中等占用混合 |
| T03 | 一次完成的 APB 访问；计时器在固定负载中的倒计数活动计入该访问序列的总能耗 |
| T04 | 一次成功输出；固定竞争强度与背压分布 |
| T05 | 一次成功读出且对应先前成功写入；功能负载覆盖多个非锁相频率比，冻结 PPA/功耗负载固定 `wr_clk=1.0 GHz`、`rd_clk=1.0 GHz` 且两域独立持续运行 |
| T06 | 一次完成的 AXI 读或写；固定读写、等待、错误和背压比例 |
| T07 | 一次完成的 CPU 请求；固定读写、命中、干净/脏缺失比例 |
| T08 | 一个成功接收的帧体字节；固定 TX/RX 帧、VLAN 拒绝及恢复负载；三个独立 1 GHz 时钟，计入两块 SRAM 的活动功耗 |
| T09 | 一条正常退休指令；固定整数、分支、load/store 比例和数据端等待分布 |
| T10 | 一个完成的 16×16 输出块；十种模式、正常活动值、独立 A/B scale 与随机正负；必须在持续输入/四槽输出稳态窗口测量，计入多块并行与背压恢复能耗。负载的种子、块数与门级验证结果在冻结 PPA 基线时一同发布 |

`N_ops` 由评测方在门级测试平台的端口握手、采样事件或 CPU 退休事件中自动计数；固定负载的活动比例避免通过选择容易的操作降低能耗。对停顿较长的实现，窗口时长增大，因此能耗/操作会反映吞吐损失。初始复位、加载程序和测试平台初始化不计入功耗窗口；负载内的运行中复位及重启开销按同一规则计入所有候选。

### PPA 分数和时间的关系

每题预先冻结一个由独立参考实现测得的正数三元组 `(A_ref,D_ref,E_ref)`。参考实现必须功能全通过、满足 setup/hold、DRC 与周期约束且代码经同行评审，防止以臃肿基线虚增分数。对于候选的正数 `(A,D,E)`，令 `S`、`H` 分别为三种子中最差的 setup、hold slack（ns），定义 `D_eff = D + max(0,-H)`、`D_setup = T_common + max(0,-S)`。Hold 违例通过 `D_eff` 连续增加等效延迟；setup 违例除已进入三种子中位关键路径延迟 `D` 外，再按最差 seed 实际最高频率相对 1 GHz 目标的比例施加四次方连续惩罚：

```text
S_base = clamp(35 × clip(A_ref/A,0.5,2)^0.35
                  × clip(D_ref/D_eff,0,2)^0.35
                  × clip(E_ref/E,0.5,2)^0.30, 0, 50)
F_setup = 1                                      if S >= 0
          (T_common/D_setup)^4                   if S < 0
S_PPA  = S_base × F_setup
                  × (0.5 if any routed seed has DRC violations else 1.0)
```

参考实现得到 35/50 分；相较参考实现的优化可升至 50。面积和能耗的比值裁剪到 `[0.5,2.0]`；延迟比值只设上限 2。满足 setup 时 `F_setup=1`；违例时 `T_common/D` 等于实际最高频率相对目标频率的比例，四次方使违例越大分数越快但连续地下降。任何种子存在 DRC 时，在连续 timing/面积/能耗得分基础上统一乘 0.5，而不是直接归零。无法合法完成布线或无有效功耗活动的**候选原因**才导致 PPA=0；工具原因导致无有效分数，应修正后对全部提交重跑。

排名用[PPA 分档](#分层评分与排名)处理测量精度，目标分辨率为 `q=1.25` 分；同档才以完成时间排序。冻结前须在目标配置上评估跨种子、跨机器和跨工具镜像的重复性，并同时公开分档边界及原始 PPA 分数。若候选最终提前完成，但未全功能通过，时间仍被记录却不获时间分。完成时间分采用[统一规则](#分层评分与排名)的 `5 × (1 − t/T_max)`，仅用作排序的最后一层。

### 防止 PPA 游戏化

- 不允许候选读取功耗种子或针对测试名/固定 PC 做特化；所有 PPA 工作负载仍验证功能。
- 不允许通过改变接口时序、引入违反题卡的额外流水级或延后响应降低功耗；相应功能/性能门禁先判定。
- 禁止参赛者提交自己的 SDC、Liberty、物理约束或替换映射单元；只提交 RTL 和验证交付物。
- 保存三个布线种子的原始报告、功耗注释率、工作负载 hash 与抽取脚本输出，便于审计。

## 领域与难度覆盖

本节说明[任务卡](#共享任务规则)为何能检验不同的数字 IC 设计能力。它是**需求覆盖论证**：每项能力都对应题面和独立验收组；并不声称十题覆盖全部芯片研发，也不把设计时的难度序号当成实测结果。实际难度间距须按[校准流程](#难度校准)验证。

### 覆盖范围的可核查结论

- **九类主要领域**均有专门题目：单时钟状态控制、高速串行链路 PCS、流式缓冲与仲裁、片上总线与外设、CDC、存储层次、处理器、NPU/DSP 矩阵算术。T10 补上乘法阵列和低精度浮点/块缩放。
- **时钟与状态尺度**从单寄存器、串行 bit-buffer 与对齐状态，到单时钟多状态、双异步时钟、五级流水线和 2D 波前阵列；检验的不是同一种 RTL 模板的十个变体。
- **接口与协议**包含连续串行切片、ready/valid、APB4、AXI4-Lite、line 后端和 CPU 指令/数据接口；至少三题专门施加背压、乱序到达的独立通道或外部等待。
- **横向能力**包括参数化（T02/T04/T05）、复位及事件优先级（T02–T10）、独立模型验证（全部题）、统一 ASAP7 布线后 PPA 评估（已校准题）。T10 的物理基线尚待补全。
- **难度结构**预置 1–3、4–6、7–9 三档及第十题压力项；逐题时限为 30 分钟至 4 小时，十题合计 18 小时 30 分钟。T10 是否确实难于 T09，以及更新后整体难度间距，必须用参考工程师和多种 agent 的预算内通过率、对数完成时间检验。

### 结论边界与后续扩展

十题**未覆盖** NoC、DDR/高速 I/O、DFT/扫描、低功耗多电源域、安全 IP、模拟/混合信号和真实流片签核。现阶段的结论应写成“覆盖多类常见可综合数字 RTL 设计课题”。十题已达到题量上限；如果试运行显示某一领域不能区分系统能力，需替换题目。
