# benchmark/ 维护约定

本文件补充根目录 [AGENTS.md](../AGENTS.md)，适用于本目录的任务、配置和调度代码。参赛者需要的行为与计分规则保留在 README、题面和 policy 中；本文件只列维护者执行的开发和发布检查，不进入参赛输入包。

## 文档和文件放置

- `README.md` 和 `README.en.md` 介绍任务设计、能力覆盖、评测方法与使用方式，正文保留主要论据及必要的技术背景。中英文内容保持一致，适用范围与测量条件明确。
- 开发与发布流程在本文件维护；试验记录、调参过程和开发日志按根目录的归档约定保存。
- 任务专属行为放 `tasks/Txx/`；本目录通用 policy 是预算和交付规则的共同入口。更新时核对中英文和机器配置，避免多份互相冲突的默认值。
- 模型差异收敛到 `runner/adapters.py`，运行条件放仓库外的配置。不得新增 `run_<model>_*`、单模型续跑或某一场试验专用的准备脚本。
- 试验历史、过时原型和已废弃入口保留在 Git 历史或根目录已忽略的 `archived/`。仍有消费者的函数先移入现有通用模块并迁移测试，再移除旧入口；不要保留一套名为 legacy 的并行调度系统。
- 新候选题不是正式 manifest 的一部分。没有可执行参考与验收的脑暴清单不作为发布制品；新版本开发在对应分支进行，不混入已冻结套件。

## 题目与验收发布门禁

每题的正式发布应有可执行证据，不能仅靠 README 宣称完成：

1. 题面、合法输入、接口、参数域、复位/背压、资源和每个计分项均有明确契约，验收组与计分映射一致。
2. 正确参考、公开冒烟和独立验收全部可编译、可执行；CPU 的 ACT4 配置及适用清单与实际运行一致。公开材料不含修复答案。
3. 对指定缺陷有有效见证：先确认错误变体可编译且违反规范，再验证验收器在目标检查处检出。编译失败不算检出；不能只让参考通过而没有负向约束。
4. 变异体目标沿用原开发要求：每题至少 8 个独立缺陷，T05–T10 目标至少 12 个、CPU 至少 20 个。记录有效分母与漏检范围；未完成时如实保留预发布状态，不篡改数量或默认跳过。
5. 参考 PPA 通过同题测量范围下的全部规定种子、setup/hold、DRC、活动及负载自检，原始证据在外部保存，基线登记到唯一的 `ppa-baselines.json`。
6. 准备器生成的实际工作区只包含单题允许材料；根目录/本目录 AGENTS、作者说明、验收器、参考 RTL、其他任务和模型运行记录不得进入。

任务级基线合格不等于整套发布合格。整套发布还需固定工具镜像 digest 和传递依赖、复核不同合法 RTL 写法、验证统一启动/评分/恢复流程，并提供可复现命令及最终报告 schema。缺项继续标记为设计稿或 pilot，不发布正式榜单。

## 物理参数探索与冻结门禁

- 使用 `evaluator/score_run.py` 的参数契约和各题的专属 PPA 契约；先确定要改的是公共参数还是已声明的任务例外。不得按模型调整约束，不能将 T10 单 PE 参数直接替换为其他任务默认值。
- 调参先用小规模参考筛选，再验证全部受影响任务及合法替代写法。保留失败组合及选择理由；参考满足约束后才更新基线，候选的连续扣分规则不得被参考资格门槛取代。
- 核对实际工具支持的随机化阶段。传入布线种子不等于完成独立随机放置，报告和实验标签须对应实际行为。
- 工具、库、SDC、物理参数、测量范围或功耗负载变化时，沿依赖判断哪些资格失效，重新执行相应资格流程。不能只重新生成哈希来消除 drift。
- `freeze_tasks.py` 是验证/发布冻结记录的入口。修改冻结依赖后先检查差异是否影响行为或测量；不影响的文档/打包调整也要通过相关回归，说明未改变的条件，再更新记录。

## 试跑校准与结果发布

- 难度结论先有预定实验计划。原发布目标是至少两种 coding agent 各三次独立试跑；没有相应授权时只完成准备和开发检查，不自行发动付费试验。
- 记录并比较全部计划样本的预算内通过情况、完成时间和错误类别。统计报告按预定重复设计给出不确定性，不能拿单次 pilot 的小分差宣布排名优势。
- 验收器修复先列受影响任务和保留提交，再统一复核；共享错误只修公共层。只重跑失效部分，不因功能补测自动启动模型或 PPA。
- 最终结果由统一发布器生成，遵守根 AGENTS 的文件白名单。删除历史入口时，不得改动既有模型分数或重写原始现场。

## 本目录变更的检查顺序

1. 运行直接相关的准备器、公开 EDA、runner 或规范检查测试；模型调用用假 CLI，EDA 打包测试用最小公共资产。
2. 检查生成工作区，而不只检查源文档。覆盖不同任务及语言，确认作者文件和答案仍被隔离；公开 EDA 只能复制通用脚本和工艺输入，不能挂载整棵 ORFS 工作树。
3. 公共准备器、容器或调度逻辑变化后，执行 benchmark 回归及受影响的 evaluator 测试；规范与冻结校验在同一拟提交树上执行。
4. 最后搜索旧入口的 import、命令示例和文档链接。移除真实消费者后才归档脚本及只服务旧实现的测试，不能留下通过导入 archived 兜底的路径。
