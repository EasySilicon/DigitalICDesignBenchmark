# 评测与评分方法

## 目标和实验轨道

主要问题是：在同等可见信息、工具和预算下，多 Agent 系统是否提高**一次提交的可验收交付质量**。排名严格按**功能正确性 → PPA → 完成时间**，具体规则见下文。产品轨道让各系统使用其原生模型，以相同费用和时限比较实际产品效果；控制轨道仅纳入能接入同一基础模型快照、采样设置和 API 的系统，用于分析编排和工程流程的影响。两条轨道的分数不得合并，也不得由产品轨道的差异单独归因于多 Agent 编排。每个任务至少独立运行 5 次，随机种子预先固定且各系统相同；报告逐题中位数、一次通过率、平均分、成本和耗时，而非只挑最好的一次。

各运行从同一只读起点复制为独立工作区。Agent 看到完整规范、公开测试和本地工具；封闭测试、参考模型、变异体以及评分脚本不进入工作区。禁止在执行中访问其他参赛工作区、隐藏验收器或历史解答。CVDP 原题在原有分数之外单独标注为公开数据集题。所有系统都可自选内部角色数和分工；计费 token、工具调用、并行资源和时钟均计入同一上限。

每题须启动**全新会话**，只注入该题的固定提示和公开文件；上一题结束后保存提交快照与计时日志，再销毁其会话和可写工作区，下一题不得调用 `resume`、`fork` 或读取历史对话。对 Codex CLI，试跑使用每题一个新的 `codex exec --ephemeral` 进程。[官方 CLI 参考](https://learn.chatgpt.com/docs/developer-commands?surface=cli)将 `--ephemeral` 定义为不把会话记录持久化到磁盘；它不能隔离文件系统。正式评测还须给每题独立容器或等效权限边界，使用本题专属临时用户配置目录，只注入相同的只读工具配置与认证；挂载只读公共起点和本题可写目录，屏蔽其他题、历史解答、全局记忆及私有验收目录，并在任务结束后撤销访问。仅靠更换工作目录或提示词不得宣称完成环境隔离。

## 资源约束

| 项目 | 固定规则 |
| --- | --- |
| 单次运行计算资源 | 16 vCPU、32 GiB RAM、100 GiB 可写盘；无 GPU、无 FPGA、无商用 EDA 许可 |
| 网络 | 仅允许事先声明的模型 API；依赖、工具链、ACT4 及参考资料均预装并锁版本 |
| 开发时钟 | 从题目与工作区交付开始计时；[清单](manifest.yaml)中的各题时限到点自动冻结文件快照 |
| 模型预算 | 控制轨道按[清单](manifest.yaml)中的累计输入+输出 token 上限运行；产品轨道按同一美元推理费用上限运行，费用上限须在模型与单价快照确定后统一公布 |
| 工具预算 | 同容器、同 CPU/RAM 限额；编译、仿真和脚本都计入时钟与资源用量 |
| 提交 | `rtl/`、`rtl/files.f`、`verif/`、`README.md` 和一个无交互 `run.sh`；由评测器冻结并复制到隔离环境；接口按[验证与交付契约](verification-contract.md) |
| 硬件资源 | 各题见[任务卡](tasks.md)。RTL 必须可综合，不得靠测试环境 DPI、文件 I/O、延时或未声明的黑盒实现功能 |

上表中的时限和控制轨道 token 上限是首轮工程预算，发布前须试做校准；产品轨道的美元上限尚待模型与价格快照，因此 **v0.2 不允许据此宣称公平的正式排名**。模型调用记录必须能审计输入、输出 token 和费用，但不得泄露题目隐藏数据。

### 工具链锁定

评测镜像应固定 OCI digest，以及 Verilator、Yosys、OpenROAD、ASAP7 工艺文件、C++ 编译器、Python/cocotb、RISC-V GCC/LLVM、Sail、ACT4 的精确修订；不单独依赖另一套 STA 程序。默认以本机 Verilator 5.051 devel 做兼容性预检；正式评测使用一个确定的镜像，不跟随本机升级。每个任务的参考实现、公开测试、隐藏测试和 PPA 流程都在该镜像内试运行。UVM、SVA 和覆盖率能力按**实际使用的语法**做冒烟验证，测试运行时不得将不支持的语法静默屏蔽。

## 输入、输出与规范优先级

原创题以[任务卡](tasks.md)为唯一规范，公开测试只是示例，不得反向增加限制。CVDP 题由锁定的原始 `input.prompt`、原始接口和任务卡中的**明确补充**构成；如补充与原文冲突，以明确补充为准，并报告为“CVDP 衍生题”，不得宣称该分数是 CVDP 官方得分。所有时序要求以有效时钟沿前采样输入、沿后检查寄存输出为准；握手在上升沿 `valid && ready` 时发生。未规定的非法输入不计分，除非任务卡写明结果。

`run.sh` 要返回非零退出码报告失败，固定随机种子可由环境变量 `BENCH_SEED` 覆盖，输出一份机器可读 `results.json`，包含测试名、通过状态、种子、工具版本、耗时；T09 还须提供 `--elf` 入口，详见[契约](verification-contract.md)。Agent 在同一时限内必须自行编写验证环境、用其定位并修复 RTL 缺陷，并使用本机 PPA 工具探索至少一个候选实现或配置效果；PPA 约束不可作为提交物覆盖官方配置。完成时间从题目发放开始，到参赛系统明确提交最终文件快照为止；到点未提交则冻结当时文件。该时间包含模型推理、内部协作、编译、仿真、PPA 探索和重试，排除评测器排队与隐藏测试运行。禁止修改评测器、隐藏测试、工具二进制或检查脚本；检测到改动或试图读取隔离路径，整次运行记 0 并记录证据。其他失败应按下面的分项规则保留部分分。

## 分层评分与排名

每题保留便于阅读的 100 分显示分，但**正式排序使用分层比较**，不能用总分把功能缺陷与 PPA 或速度互相抵消。

| 层级 | 显示分 | 进入条件 | 自动验收方式 |
| --- | ---: | --- | --- |
| ① 功能正确性 F+P | 75 | 所有有效提交 | F=60：基本行为；P=15：协议、边界和异常。各任务卡分配具体子项 |
| ② PPA | 20 | F+P=75、交付合格且通过综合/接口门禁 | 统一 PDK、SDC、活动负载下测面积、关键路径和每有用操作能耗；算法见[PPA 方法](ppa.md) |
| ③ 完成时间 | 5 | F+P=75、交付合格且 PPA 有效 | `5 × (1 − t/T_max)`，裁剪到 0–5；`t` 是最终提交墙钟时间，`T_max` 为该题时限 |

每个 F/P 子项只有在其定义的测试组通过时得分；随机测试以固定隐藏种子组执行，**不得按测试数量让某一细节主导权重**。单项可设 0、半分、全分三个档位：全部通过取全分，至少一半的独立场景通过且无错误接收/错误提交等安全类缺陷取半分，否则 0。安全类缺陷所在子项直接 0。完整公开测试的分数不超过 F/P 的 20%；隐藏测试给出可重现失败摘要，但不公开全部向量。**只有 F+P=75 才算功能全通过**；其余运行的 PPA、时间显示分均为 0，但仍记录诊断测量。

**单题排序**依次比较 `(F+P 得分，PPA 排名分档，完成时间较短者优先)`。PPA 原始分照常报告；排名时按预先冻结的分辨率 `q` 计算 `PPA 排名分档 = min(floor(20/q + 0.5), floor(PPA 原始分/q + 0.5))`，同档才比较时间。试评分 `q=0.5` 分，九题参考实现的三种子单次分数跨度最大为 0.110 分；正式版仍须用跨机器和跨工具重复性数据复核。采用分档使排名具有一致、可传递的顺序。**套题排序**先比较功能全通过题数，再比较十题 F+P 总和；仍相同时比较所有功能全通过题的 PPA 排名分档总和，最后比较这些题的 `t/T_max` 总和。若全通过题集合不同，PPA 均已按各题参考设计归一化；同时报告逐题数据。100 分显示分只用于可视化，不作为排序键。

### 交付准入与失败处理

1. 找不到顶层、无法 elaboration 或接口不符时，F+P=0；保留诊断日志。候选 RTL 有锁存、仿真专用捷径、未声明黑盒，或在综合路径使用 `#delay`、`force`、文件 I/O 时，不可进入 PPA 排名，并标记交付不合格。
2. 参赛系统必须提交可运行的自检入口、至少一项自检、使用说明、PPA 探索记录和可综合 RTL。T09 的自检还须加载评测方提供的任意合法 ELF。缺失时独立功能测试仍运行并报告 RTL 分数，但该运行标记为**交付不合格**，不进入完整交付主榜及 PPA/时间排序。自检质量的变异检出率另作诊断；正式阈值须经变异体校准后冻结。
3. **行为 oracle 不得依赖 DUT 内部信号**。自带断言可观察内部设计；独立行为评分通过约定端口和 CPU 提交端口进行。T06 的 CDC 结构、T09 的五级结构、T10 的脉动 PE 邻接结构与资源边界按冻结的静态规则和人工复核检查。评测器不执行候选自带验证代码来判断其 RTL 正确性；候选 UT 在单独的交付检查和变异体试验中运行。
4. 功能测试超时或死锁只扣相关功能点，不一票否决其他独立点；CPU 的架构程序与流水线专项分别记分。

架构资源边界（例如不加片内大 ROM、缓存容量不超规格）是功能/交付门禁，单元面积则由统一 PPA 流程比较。静态工具告警必须按规则分类；有理由的工具误报由评审复现后记录豁免，所有系统相同。禁止由人工仅凭代码风格主观加减分。

### 自带测试与变异测试

每题由 benchmark 团队制作至少 8 个**独立缺陷变异体**，覆盖优先级、位宽、时序、边界、复位等不同错误；T06–T10 至少 12 个，CPU 至少 20 个。变异体只用于评估参赛者的 `verif/`，不交给参赛者。只有参考实现通过测试、变异体本身可编译且确实违反规范的变异体才计入分母。记录 `killed/eligible`、参考实现误报数、需求到测试映射和功能覆盖率；这些是**交付质量诊断指标**，不抵消功能、PPA 或时间的排序优先级。

## 验收器独立性和争议处理

- 每题至少有一个与 RTL 结构无关的参考模型；组合题用穷举，顺序题用事务级 Python 模型，CPU 用 Sail/ACT4 加独立提交差分。不能只拿另一个 RTL 实现当唯一 oracle。
- 公布前对参考实现、朴素错误实现和变异体执行测试；参考实现必须全通过，错误实现必须至少在对应点失败。所有隐藏种子和预期结果固定、可重放。
- Verilator 是两态仿真；不能把未知值检查作为唯一检错方法。复位前输出、未复位 RAM 内容和未规定信号不评分。
- 争议只复核规范、评测器及冻结提交。若题目歧义或评测器缺陷影响所有系统，应修订版本号并**重跑全部系统**，不针对单一系统改规则。

## 难度校准

在正式排名前，用至少 2 名有经验 RTL 工程师分别试做每题，再用至少 2 种 coding agent 做不少于 3 次试运行。记录完成时间、F+P 得分、常见失败、人工澄清次数和测试器误判。目标是从 T01 到 T10 逐步增加中位完成时间并降低预算内通过率；如果相邻题的经验难度倒置或某题全部系统 0 分，调整题面、预算或换题，再冻结新版本。难度“均匀”以试运行的**预算内通过率区间和对数完成时间**来检查，不能由任务名称主观断定。

## 统计报告

主指标为“F+P=75/75”的一次全功能通过率与十题功能全通过题数；仅在上述指标相同或分层比较需要时，比较已通过题的 PPA，再比较完成时间。补充展示逐题 F/P、面积、关键路径、平均功率与能耗/操作、PPA 得分、提交成功率、交付合格率、变异检出率、开发耗时、模型 token/费用及工具 CPU 时间。公开 CVDP 两题与原创八题分别报告；另报告难度 1–3、4–6、7–9 三档及 T10 压力项。用相同随机种子配对系统结果，给出置信区间；10 题规模有限，不能仅凭总分的小差距声称统计优势。

## 发布门禁

正式发布版本必须同时具备：10 个冻结题目工作区；10 个可编译参考实现；10 个公开冒烟测试和独立隐藏验收器；变异体集合及有效性日志；固定工具镜像 digest；公开工艺、PPA 约束/负载/参考值、功耗注释率和重复性报告；CVDP 来源/许可核对；ACT4 适用清单及 CPU 配置；产品轨道模型及单价快照、统一费用上限；人工试做与 agent 试运行报告；可复现的一键评分及机器可读报告 schema。任一项缺失只可标为设计稿或试运行版，不生成正式榜单。
