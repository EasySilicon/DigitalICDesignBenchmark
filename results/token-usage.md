## 口径说明（重要：各家统计口径不同，横向只看量级）

- **DeepSeek V4.1 Flash**：2026-10-04 早期试跑的会话日志未保留，无 token 数据。
- **Kimi K3**：从 Kimi Code 会话日志逐轮累加（inputOther + output + inputCacheRead + inputCacheCreation），**含缓存读**；输出 token 仅占零头（如 T01 输出仅 1.7 万）。
- **GLM-5.3 / GLM-5.3F / Kimi K3.1 Pro**：取自评测框架 `agent_result.json` 的 `tokens` 字段，**全口径（输入含缓存读 + 输出）**。
  - 对账示例（GLM-5.3 T02）：记录 206 万 = 输入 202 万（其中缓存读 196 万）+ 输出 4.3 万；不含缓存读的「新输入+输出」仅 10.1 万。
- **GPT-6-Astra / GPT-6.1-Sol**：取自 Codex 会话日志末尾 CLI 自报的 "tokens used"（旧版评测脚本 run_suite.py 第 195 行即按此解析）。**大概率只计新输入 + 输出，不含缓存命中部分**（每轮明细未保留，无法逐项对账；量级佐证：Astra T09 写 CPU 长达 120 分钟仅 17.9 万，若含缓存读低得不合理）。
- **Claude Sonnet 5.5 / Opus 5.5**：取自评测框架 `agent_result.json`（Claude 适配器对每轮 usage 的 input + cache_creation + cache_read + output 四项求和），**含缓存读**。
- **缺失说明**：GLM-5.3 / GLM-5.3F 的 T01 均撞 30 分钟墙被杀（exit 124），token 未落盘；GLM-5.3F 的 T09/T10 同样撞时限墙（7200s/14400s）。
